Module 1

Salesforce Platform Fundamentals

Before writing tests, understand what Salesforce is doing underneath the UI.

1.1 What is Salesforce?

Salesforce is a cloud CRM platform used to manage sales, service, marketing, support, and custom business workflows. For testers, the important part is that Salesforce behavior is produced by a mix of data, metadata, permissions, declarative automation, and custom code.

SaaS Layer

Ready-to-use applications such as Sales Cloud and Service Cloud. QA focuses on business journeys like lead conversion, opportunity stages, case routing, approvals, and reports.

PaaS Layer

Custom objects, Apex, Lightning Web Components, Flows, validation rules, and integrations. QA validates both visible UI behavior and hidden record side effects.

1.2 Standard Objects and QA Focus

ObjectBusiness RoleQA Focus
LeadRaw prospectCreate, validate, convert, duplicate checks
AccountCompany or customerHierarchy, ownership, related contacts
ContactPerson linked to accountRequired fields, duplicate rules, relationships
OpportunitySales dealStage changes, amount, close date, approvals
CaseSupport ticketAssignment rules, SLA, status flow, queues
Testing rule: Always connect a UI step to a business result. A successful click is not enough; verify the record, relationship, status, owner, or downstream effect.

1.3 Salesforce Automation Flow Example

A real Salesforce test usually crosses multiple layers. In a Lead conversion journey, the tester creates a Lead, qualifies it, converts it, and then validates that Salesforce created the Account, Contact, and optionally Opportunity records correctly. The UI may show only a success message, but the real business proof is in the related records and field values.

Arrange

Create a Lead with required fields such as company, last name, lead source, status, and owner.

Act

Open the Lead as a sales user, click Convert, choose conversion options, and confirm.

Assert

Verify converted status, Account, Contact, Opportunity, owner, and any automation-created task.

Module 2

Core QA Domain Knowledge

Know the environment, users, permissions, and data model before automation begins.

2.1 Sandbox Strategy

DeveloperFeature smoke
Dev ProSmall integration
Partial CopyDaily regression
Full SandboxPre-release validation

Choose the sandbox by test purpose. Developer sandboxes are fast and isolated, but their data is limited. Partial Copy sandboxes are useful for CI regression because they contain realistic sample data. Full sandboxes are expensive and should be used for staging, release rehearsal, and high-confidence validation.

2.2 Security Layers

Profile

Base permissions, object access, app access, and field-level security.

Permission Set

Extra access assigned without changing a user's base profile.

Sharing Rule

Controls which records a user can see after object access is granted.

Common defect: A test passes as admin but fails for a standard user. Persona-based automation is mandatory for Salesforce projects.

2.3 Persona-Based Test Matrix

Salesforce teams usually test the same feature with different personas because each user can see different apps, tabs, fields, buttons, list views, and records. A good automation suite does not only run as System Administrator.

PersonaExample ChecksAutomation Risk
Sales RepCreate Lead, update Opportunity, log activityCannot see manager-only fields or reports
Sales ManagerApprove discounts, view team pipelineNeeds role hierarchy and sharing data
Support AgentAccept Case, change status, add commentsQueue assignment and service console behavior
AdminSetup validation, metadata visibilityToo much access can hide real permission defects

2.4 Release and Regression Planning

  • Run smoke tests after every deployment to validate critical business paths.
  • Run regression tests nightly or before major UAT handoff.
  • Track metadata changes such as fields, flows, layouts, and permission sets.
  • Keep test records tagged with a run ID so failures can be traced quickly.

Module 3

Salesforce UI Automation

Build reliable browser automation for Lightning pages without depending on fragile generated IDs.

3.1 Lightning Challenges

  • Dynamic component rendering and delayed page hydration.
  • Generated element IDs that change between sessions.
  • Lookup fields, comboboxes, modals, tabs, and related lists.
  • Background flows and triggers that update records after save.
Java - stable wait pattern
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(20));

WebElement toast = wait.until(ExpectedConditions.visibilityOfElementLocated(
    By.xpath("//span[contains(@class,'toastMessage')]")
));

assertTrue(toast.getText().contains("saved"));

3.2 Selector Principles

Prefer accessible names, labels, button text, stable custom test attributes, and business-visible values. Avoid absolute XPath, generated IDs, and position-based selectors because Salesforce metadata changes can reorder fields and components.

3.3 Common Lightning Components

ComponentAutomation ApproachValidation Example
LookupSearch by visible label, select result textAccount lookup shows selected account pill
ComboboxOpen dropdown, select visible optionOpportunity Stage changes to Proposal
ToastWait for visible success or error messageRecord saved confirmation appears
Related ListWait for row with expected related recordConverted Contact appears under Account
ModalScope selectors inside modal containerNew Case modal saves and closes

3.4 Example UI Scenarios

Lead Conversion Smoke

Open a prepared Lead, convert it, confirm success toast, then validate Account and Contact creation through UI and API.

Case Status Regression

Create a Case, assign queue, move status from New to Working to Closed, and verify SLA fields and history tracking.

Module 4

Java Test Framework Design

Organize tests so they read like business flows and scale across teams.

Page Object Model

Put repeated UI operations into focused page or component classes: LoginPage, AppLauncher, LeadPage, RecordModal, ToastMessage, and RelatedList.

Test Data Factory

Generate unique leads, accounts, cases, and opportunities with predictable fields and a run ID for cleanup and debugging.

Suggested project structure
src/test/java
  tests/smoke
  tests/regression
  pages/lightning
  components
  services/salesforce
  data/factory
  listeners
  reports
  • Keep test names focused on business scenarios.
  • Use TestNG groups for smoke, regression, api, and release.
  • Capture screenshots and logs on every failure.
  • Never share WebDriver state across parallel tests.

4.1 Framework Layers

LayerResponsibilityExample
TestBusiness scenario and assertionsconvertQualifiedLeadCreatesOpportunity()
PageScreen-level actionsLeadPage.clickConvert()
ComponentReusable Lightning widgetsLookup.select("Acme")
ServiceAPI setup and validationSalesforceApi.createAccount()
FactoryData object creationLeadFactory.qualifiedLead()
Java - readable business test
@Test(groups = {"smoke", "sales"})
public void convertQualifiedLeadCreatesOpportunity() {
    Lead lead = leadFactory.createQualifiedLead();

    leadPage.open(lead.id());
    leadPage.convertLead();

    assertThat(api.getLead(lead.id()).isConverted()).isTrue();
    assertThat(api.findOpportunityByLead(lead.id())).isPresent();
}

Module 5

BDD with Cucumber

Write feature files that document Salesforce behavior without hiding test logic.

BDD is useful when business analysts, admins, QA engineers, and developers need one shared language. Good feature files describe the business rule; step definitions perform the automation.

Gherkin - lead conversion
Feature: Lead conversion

  @smoke @sales
  Scenario: Convert a qualified lead into account and opportunity
    Given a qualified lead exists
    When the sales user converts the lead
    Then an account should be created
    And an opportunity should be linked to the account

@smoke

Runs before release or deployment for critical paths.

@regression

Runs broader business workflows, usually nightly.

@persona

Runs the same feature as admin, manager, or standard user.

5.1 Step Definition Design

Step definitions should call page objects and services, not contain long Selenium code directly. This keeps the Gherkin readable and keeps automation logic reusable across scenarios.

Java - Cucumber step definition
@Given("a qualified lead exists")
public void qualifiedLeadExists() {
    testContext.lead = leadFactory.createQualifiedLead();
}

@When("the sales user converts the lead")
public void salesUserConvertsLead() {
    leadPage.open(testContext.lead.id());
    leadPage.convertLead();
}

5.2 Good Feature File Rules

  • Use business language, not locator or button implementation details.
  • Keep Background steps short and only for shared context.
  • Use Scenario Outline for repeated record types or personas.
  • Use tags to control CI execution instead of separate duplicate feature files.

Module 6

API Testing and Test Data

Use API setup and validation to make UI tests faster, cleaner, and more reliable.

6.1 API-First Data Setup

UI automation should not spend most of its time creating prerequisite data. Use Salesforce REST API or backend helpers to create records, then use the UI only for the journey being tested.

REST Assured - create account
given()
  .header("Authorization", "Bearer " + accessToken)
  .contentType("application/json")
  .body(Map.of("Name", "AUTO_QA_Account"))
.when()
  .post(instanceUrl + "/services/data/v60.0/sobjects/Account")
.then()
  .statusCode(201);
Pattern: Arrange through API, act through UI, assert through UI and API. This keeps browser time focused on the behavior users actually perform.

6.2 Salesforce API Validations

API checks are especially useful when a UI action triggers hidden automation. For example, closing an Opportunity can create a task, update forecast fields, notify an integration, or change approval status. The UI may not show all of those changes immediately.

UI ActionAPI ValidationWhy It Matters
Convert LeadQuery Account, Contact, OpportunityConfirms full conversion result
Close CaseQuery Status, ClosedDate, OwnerIdConfirms service workflow completed
Submit ApprovalQuery ProcessInstanceConfirms approval process started
Update Opportunity StageQuery StageName and ForecastCategoryConfirms sales reporting data

Module 7

CI/CD and Reporting

Turn local automation into release feedback your team can trust.

7.1 Pipeline Stages

1

Checkout and build. Pull the test framework and compile dependencies.

2

Validate secrets. Confirm org URL, username, token, and connected app config.

3

Run tagged suites. Execute smoke on deployment candidates and regression nightly.

4

Publish artifacts. Store reports, screenshots, logs, and record IDs.

Jenkinsfile - simple stages
pipeline {
  agent any
  stages {
    stage('Build') { steps { sh 'mvn clean compile' } }
    stage('API') { steps { sh 'mvn test -Dgroups=api' } }
    stage('Smoke') { steps { sh 'mvn test -Dgroups=smoke' } }
  }
  post {
    always {
      junit 'target/surefire-reports/*.xml'
      archiveArtifacts 'target/screenshots/**'
    }
  }
}

7.2 Report Triage Workflow

A good report should help the team decide what happened without rerunning the test immediately. Store the current user, org URL, record IDs, screenshot, console logs, API response summary, and exact suite tag. Failures should be classified as product defect, environment issue, data issue, or automation defect.

Release Gate

Block deployment when a critical smoke flow fails: login, lead conversion, case routing, approval, or payment-related integration.

Quarantine Rule

A flaky test can be temporarily quarantined only with an owner, ticket, reason, and target fix date. Do not silently ignore it.

Module 8

Interview Q&A

Short answers for Salesforce QA automation interviews.

What makes Salesforce automation different from normal web automation?

Salesforce uses metadata-driven screens, dynamic Lightning components, permissions, record types, background automation, and org-specific configuration. Tests need stable waits, role-based coverage, API setup, and business-state assertions.

How do you reduce flaky Salesforce UI tests?

Wait for visible business states, avoid generated IDs, isolate data, run tests with dedicated users, capture artifacts, and classify failures as product, environment, or automation issues.

Why use API seeding?

API seeding creates prerequisite records quickly and reliably, leaving browser automation to validate the user workflow. It also makes data setup more traceable through run IDs.

How do you design release smoke tests?

Keep them short and critical: login, navigation, record create, update, approval or conversion path, and API validation. Smoke suites should block releases only when the failure matters.

How do record types affect automation?

Record types can change picklist values, page layouts, required fields, business processes, and automation paths. Test data factories should explicitly create records with the correct record type instead of relying on user defaults.

How do you test validation rules?

Create both positive and negative cases. A positive test saves a valid record successfully. A negative test enters invalid data and verifies the exact field-level or page-level error message without creating a record.

How do you handle Salesforce flows in testing?

Treat flows as business automation. Verify the trigger condition, the changed fields, created related records, emails, approval routing, or assignment behavior. Use API queries when the flow result is not fully visible in the UI.

What should be included in a Salesforce automation failure log?

Include org URL, user persona, test run ID, record IDs, current page URL, screenshot, browser logs, API response summaries, and the metadata or permission set assumptions for that test.
